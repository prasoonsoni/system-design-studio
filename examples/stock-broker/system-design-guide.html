Stock Broker Trading Platform

An end-to-end design for a retail brokerage that lets users trade equities and derivatives on an exchange — covering requirements, capacity, architecture, schema design, API design, and the reliability, scaling and compliance concerns that make this domain hard. The governing idea: the broker is not the exchange. Matching happens at the exchange; the broker does auth, funds, risk, routing, market-data distribution and settlement around it.

01Overview

A brokerage platform is an intermediary between retail users and one or more exchanges (NSE/BSE, NYSE/NASDAQ). Users deposit money, place orders, and hold positions; the platform validates and risk-checks each order, routes it to the exchange, tracks its outcome, and keeps the user's money and holdings correct.

The one idea to anchor everything

The broker never matches buy and sell orders — that is the exchange's matching engine, using price-time priority. The broker's surface area is everything around matching: identity, funds, risk, order management, exchange connectivity, market-data fan-out, portfolio, and post-trade settlement & reconciliation.

In scope

  • Equity delivery + intraday, and F&O (futures & options) trading.
  • Order management, real-time market data, portfolio & P&L, funds, statements.
  • Regulatory audit, reconciliation, and surveillance hooks.

Out of scope (assumptions)

  • We do not build a matching engine — we integrate with the exchange over FIX.
  • Payment-gateway internals, KYC-provider internals, and mutual-fund/IPO flows are treated as external integrations.

Takeaway

The order plane is modest in QPS but demands correctness & low latency; the data plane is enormous in throughput/fan-out but tolerates loss. Designing them as one system is the classic mistake — they scale on different axes and get different guarantees.

04High-Level Architecture

Two planes, deliberately separated at the edge so the read-heavy quote firehose never contends with the correctness-critical order path.

Order / control plane CP

Client → API Gateway → OMS (order state machine) → RMS (risk gate) + Funds/Ledger (block money) → Exchange Gateway (FIX) → Exchange. Execution reports flow back through the Exchange Gateway to the OMS, which emits events to Kafka. Consumers (Portfolio, Notifications, Reporting, Ledger-settlement) react asynchronously.

Market-data plane AP

Exchange feed (UDP multicast) → Market Data Service (decode, normalise, build depth & candles) → Redis (last-value cache) + Kafka (stream) + TSDB (history) → WebSocket Gateway → clients. Read-only, massive fan-out, conflated for slow consumers.

Event backbone

Kafka is the spine. Producers (OMS, Funds, Market Data) publish; independent consumer groups (Portfolio, Notifications, Reporting) read. Partitioned by user_id (order/funds events, preserving per-user ordering) or token (ticks). Durable and replayable — the basis for reconciliation and rebuilding downstream stores.

05Component Deep-Dives

Order Management Service (OMS)

The heart of the platform. It owns every order's deterministic state machine and is the orchestrator of the placement saga.

  • State machine: PENDING → VALIDATED → SENT → OPEN → PARTIALLY_FILLED → FILLED, with terminal branches REJECTED, CANCELLED, EXPIRED, and transient PENDING_CANCEL/PENDING_MODIFY.
  • Write-ahead: every transition is persisted before the side-effect (RMS call, FIX send), so a crash recovers deterministically — no order lost or double-sent.
  • Idempotency: a unique constraint on (user_id, client_order_id) makes retries safe at the database level.
  • ID mapping: maintains internal ↔ exchange order-ID mapping to correlate execution reports, modifies and cancels.

Risk Management Service (RMS)

A synchronous, blocking gate on the order path plus continuous post-trade monitoring.

  • Pre-trade: margin sufficiency, exposure & position limits, banned/illiquid scrips, price bands / circuit limits.
  • Margin model: full cash for CNC delivery; leverage for MIS; SPAN + Exposure for derivatives.
  • Hot path: keeps positions/limits in memory (refreshed from Kafka position events); it sits on the latency-critical path, so it must not do slow I/O.
  • Post-trade: monitors live margin, auto-square-off on breach.

Funds & Ledger

The authoritative money service, built on a double-entry ledger: every movement is a balanced set of debits and credits, append-only and auditable. Funds are blocked on placement, settled against the actual fill, and the remainder released on cancel/partial. Row-level locking (or optimistic concurrency) prevents the same balance being spent twice.

Exchange Gateway

Translates internal orders to the exchange protocol and holds the live session. Speaks FIX over a stateful, sequenced session — sequence numbers, heartbeats (35=0), and gap-fill/resend (35=2) on disconnect. Runs active–passive with sequence-number continuity for failover, guaranteeing strict ordering and no message loss. Handles async ExecutionReport (35=8) messages: fills, partials, rejects, cancels.

Market Data Service

Ingests the raw exchange feed (often UDP multicast), decodes the binary format, normalises symbols, builds top-of-book/depth and OHLC candles. Publishes latest tick to Redis (last-value cache), the stream to Kafka, and history to the TSDB. Conflates aggressively for consumers that can't keep up.

Why placement is asynchronous

The API returns 202 Accepted with status PENDING immediately — it does not block until the exchange fills. The final outcome arrives via the WebSocket order stream (or polling). This keeps the API fast and decouples the client from exchange latency.

09Consistency & Reliability

Where each guarantee applies

Orders and money are CP: correctness beats availability — a stale balance or a lost order is a real financial error. Quotes, watchlists and portfolio views are AP: a tick that's a few ms stale is fine, and availability wins.

Order placement as a saga

The OMS orchestrates a short saga: persist (PENDING) → RMS check + funds block → route to exchange. Each step has a compensating action (release funds, mark rejected) so a failure at any point leaves the system consistent. Because persistence is write-ahead, a crashed OMS recovers by replaying the last known state and reconciling with the exchange.

Idempotency & exactly-once-ish

  • Placement: unique (user_id, client_order_id) ⇒ retries can't duplicate.
  • Execution reports: unique exchange_trade_id ⇒ a re-delivered fill is ignored.
  • Consumers: dedupe on eventId ⇒ a replayed Kafka event doesn't double-count P&L or double-notify.

Failure scenarios

FailureHandling
OMS crashes mid-placementRecover from persisted state; reconcile open orders with the exchange on restart.
Exchange gateway disconnectsFIX resend/gap-fill on reconnect; active-passive failover with seq continuity.
Duplicate execution reportRejected by unique exchange_trade_id.
Kafka consumer lag/replayIdempotent consumers; replay rebuilds downstream stores safely.
Intraday margin breachRMS post-trade monitor triggers auto-square-off.
Broker/exchange mismatchEOD reconciliation against the exchange trade file flags discrepancies.

10Scaling & Performance

  • Shard orders & ledger by user_id; read replicas absorb order-book/portfolio reads. A single user's data stays co-located, so per-user transactions stay single-shard.
  • Stateless services autoscale; all shared state (rate limits, sessions, quotes) lives in Redis so any instance serves any user.
  • Kafka partitioning by user/token gives parallelism while preserving ordering within a key.
  • WS fan-out scales horizontally with a shared subscription store; conflation bounds memory and egress for slow consumers during volatile opens.
  • Market-open spike (10–20×): pre-scale ahead of 09:15, apply backpressure/queueing on the order path, and rate-limit per user so no client can monopolise capacity.
  • Hot-path tricks: local JWT verification at the gateway (no round trip), in-memory RMS positions, last-value quote cache in Redis.

Rule of thumb

Scale the data plane for throughput and fan-out (more WS + market-data nodes, aggressive conflation). Scale the order plane for correctness under burst (sharding, backpressure, idempotency) — not raw QPS, which is modest.

11Security & Compliance

  • AuthN/Z: short-lived JWTs, refresh rotation, 2FA, device binding; mTLS between internal services; secrets in a vault.
  • Data protection: PII and bank details encrypted at rest (field-level for the most sensitive), TLS in transit, tokenised card/bank references — never raw numbers in logs or URLs.
  • Regulatory: immutable audit log of every order/fund action; typically 7-year retention in cold storage; surveillance hooks for order-to-trade ratio, self-trades, and circuit-limit breaches.
  • Abuse & resilience: per-user rate limits, DDoS protection at the edge, and circuit breakers around the exchange link so its failure degrades gracefully rather than cascading.

12Observability

  • Golden metrics: order-placement latency (p50/p99), reject rate, fill rate, exchange round-trip, WS connection count & egress, consumer lag.
  • Tracing: a correlation/trace ID injected at the gateway follows an order across OMS → RMS → Funds → Exchange GW and into Kafka consumers.
  • Reconciliation dashboards: broker-vs-exchange trade counts, ledger debit=credit invariants, and blocked-vs-settled funds — alert on any drift.
  • Alerting: page on exchange-session down, reconciliation mismatch, RMS auto-square-off spikes, and market-open error-rate anomalies.

13Trade-offs & Talking Points

DecisionChoice & why
Monolith vs microservicesMicroservices, so the market-data plane and order plane scale independently and get different guarantees. Cost: operational complexity, distributed reasoning.
SQL vs NoSQL for ordersSQL — ACID, constraints (idempotency), and transactional funds updates matter more than write throughput here. Scale via sharding, not by dropping consistency.
Sync vs async order pathSync only for the blocking parts that must be correct before routing (RMS, funds block); everything downstream (portfolio, notifications, reporting) is async via Kafka.
Build vs buy matchingNever build a matching engine for a retail broker — route to the exchange. Building one is a different, far harder product.
Exactly-onceApproximated with idempotency keys + reconciliation rather than pursued as a distributed-systems absolute.
Internalisation (advanced)Large brokers may internalise/net some flow before routing. Powerful but adds a mini matching engine and heavy regulatory surface — out of scope here.

If you remember five things

1) Broker routes, exchange matches. 2) Split the CP order plane from the AP data plane at the edge. 3) The OMS state machine + write-ahead persistence is the correctness backbone. 4) Money is a double-entry ledger, not a balance field. 5) Idempotency + EOD reconciliation is how you get "exactly-once" in practice.
